# Trunk retrieval/scoping evaluation

## Methodology

This evaluation compares three deterministic conditions across four two-topic scenarios:

- `unforked`: topic B is answered with topic A still in context.
- `fresh-session`: topic B is answered with no memory.
- `trunk`: topic B is answered from a forked context using the shared trunk memory engine.

Metrics are marker-based:

- **contamination**: fraction of topic-A-only markers that appear in the topic-B answer. Lower is better.
- **retention**: fraction of still-relevant shared markers that appear in the topic-B answer. Higher is better.

The harness uses `InMemoryMemoryEngine`, which reuses the production pure logic for scope checks, deduplication, supersession, and promotion. Retrieval is deterministic token Jaccard over in-memory rows rather than Atlas Vector Search.

Command run:

```powershell
node packages\eval\src\run.ts
```

## How to read these numbers

**Each baseline wins exactly one metric by sacrificing the other completely.** That is the
whole point, and the aggregate table hides it:

- `unforked` retains everything (**1.00**) because it keeps the full context — and is
  contaminated by that same context (**0.77**).
- `fresh-session` is perfectly clean (**0.00**) for a trivial reason: **it has no memory at
  all.** A condition that knows nothing cannot be contaminated. It also retains nothing
  (**0.00**), which is precisely the "re-explain everything" problem Trunk exists to solve.
  Treating its contamination score as a win misreads a degenerate baseline as a strong one.
- `trunk` is the **only condition strong on both axes at once** (0.25 / 1.00). It is a Pareto
  improvement, not a clean sweep, and that is the honest claim to make.

**Trunk is perfect (0.00 contamination, 1.00 retention) on 3 of the 4 scenarios.** The entire
0.25 mean comes from one deliberately adversarial case.

### The one failure, and why it is a different problem

`cart-cache-then-ratelimit-hard` was written to be hard: topic A (cart caching) and topic B
(rate limiting) *both* legitimately involve Redis, so they share vocabulary. Retrieval pulled
true-but-irrelevant cart facts (`checkout:cart`, a 15-minute TTL) into the rate-limiter answer.

This distinction matters and is worth stating plainly:

| Problem | Does Trunk solve it? |
|---|---|
| Another branch's **hypotheses** polluting my context | **Yes** — scoping, proven by the `scope` test suite |
| A **true but irrelevant** trunk fact surfacing because it shares vocabulary | **No** — this is retrieval precision, not scoping |

Branch scoping worked exactly as designed here; no hypothesis leaked. What failed was
*ranking*. That is a known, separable problem with a known fix — hybrid vector + text
retrieval with relevance filtering (`b4-hybrid`), currently blocked on Atlas access. Claiming
this scenario as a scoping failure would be wrong, and claiming Trunk solves relevance would
be overclaiming.

## Findings

Trunk beat `unforked` on contamination by **0.52** mean points while matching its **1.00** mean retention. Trunk beat `fresh-session` on retention by **1.00** mean point, but did **not** beat it on contamination: `fresh-session` scored **0.00** and trunk scored **0.25**.

The hard `cart-cache-then-ratelimit-hard` scenario is the failure case. Topic A and topic B both discuss Redis, so deterministic retrieval pulled cart-cache facts into the rate-limit answer. This is useful evidence: branch scoping prevented hypothesis leaks, but relevance ranking still needs improvement for same-infrastructure, different-task memories.

## Limitations

This is not an end-to-end LLM quality evaluation. Answers are simulated rather than generated by a real model. The harness deterministically assembles answers from memories available to each condition, so it measures whether retrieval and scoping behave as designed, not whether a model would use those memories well.

The in-memory engine replaces Atlas Vector Search with deterministic token Jaccard retrieval. That makes the run reproducible without npm packages or MongoDB, but it is not a substitute for measuring the real embedding model and Atlas index. A full evaluation needs the Mongo-backed engine, real embeddings, actual LLM answers, repeated trials, and a judge that can detect paraphrased contamination/retention rather than only exact marker strings.

## Core contract changes needed

No `packages/core/` change was needed for this evaluation.
